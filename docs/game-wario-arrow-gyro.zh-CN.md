# Game & Wario：Arrow 靶子与体感方向校准分析

## 当前交付状态（2026-10-28）

最终保留第九轮手机确认的版本：用户短时连续射箭后确认换箭方向正常。远程姿态按顺序消费全部已收到的体感样本，关闭额外零点学习及加速度姿态反馈，原始加速度继续提供给游戏。

同时包含 VPAD 角度/方向参考实现、连续机体轴角度积分、有限旋转四元数积分，以及仅针对已匹配标题、RPX hash 和指令签名的日版举盾兼容处理。取箭和模式流程保持游戏原逻辑；Input API 日志开启时可记录传感器和真实起弓/发射数据。

Cemu.exe 与 CemuGamePad.dll 必须配套更新至 ABI 1.1。长期姿态漂移、格挡及完整端到端验收仍待验证。以下各轮记录保留排查依据，早期假设及“待复测”描述按当轮状态理解；最终状态以本节和末尾第九轮手机结果为准。

分析日期：2026-10-28。以下地址是本地 ROM 的链接时 PowerPC 虚拟地址，不是 RPX 文件偏移，也不是宿主进程地址。其他地区和版本不能直接套用这些地址。

## 分析对象与实际配置

- 日版标题：`0005000010112d00`，TitleVersion `v1`。
- 主程序：本地 `code/Slate.rpx`，文件大小 11,229,184 字节。
- SHA-256：`eed328204f776536e1071646b5d3e3a095cc65e293468bed1a351284dfa22fcc`。
- Cemu 日志确认 `Strict shader mul: true`，图形后端为 Vulkan。
- 主程序包含 `.text`、`.rodata` 及重定位表；通过解压 RPX 段、解析导入符号、解析重定位和 PowerPC 反汇编建立下面的调用链。

## ROM 中的真实调用链

1. `0x02263830–0x02263870`：Arrow 在校准流程中从控制器封装对象的 `+0x58/+0x5c/+0x60` 读取三个角度，累加进当前射击的校准记录。
2. 控制器封装中首份 `VPADStatus` 位于 `+0x14`，所以这些字段对应 `VPADStatus +0x44` 的角度，而不是触屏坐标。`0x02028990` 是其 `VPADRead` 导入调用点。
3. `0x02263874` 调用游戏的重置函数 `0x020299b0`，进入 `0x02029938`。
4. `0x02029970` 调用导入 `VPADSetGyroAngle`，三个浮点参数均为 `0.0f`；`0x0202997c` 接着调用 `VPADSetGyroDirection`；`0x02029988` 调用 `VPADSetGyroDirReviseBase`。
5. 传给方向重置接口的只读矩阵位于 `0x10001954`，内容是单位矩阵。
6. `0x0229e30c` 是碰撞分发器对靶子受击函数 `0x022b9e2c` 的调用。
7. 靶子受击函数记录校准角度并调用 `0x022b9cf4`。后者比较记录中 Y 分量的差的绝对值；关键浮点比较在 `0x022b9dac`，失败分支在 `0x022b9db0`。
8. 比较阈值由 `0x022686b4` 初始化为只读常量 `0x10021258`，位模式 `0x3d4ccccd`，即约 `0.05f`。
9. 成功后 `0x022b9f14` 设置动画索引 `3`，经 `0x022b9a4c` 和 `0x100277d8` 的动画表选择 `Target_Break_00`。普通受击选择索引 `2`，即 `Target_Hit_02`。

简化后的关键关系：

```text
发射校准：保存累计角度 → 请求角度清零和方向归位
命中靶子：记录本次校准角度
如果两次记录的 Y 角度差的绝对值 < 0.05：进入破碎动画
否则：播放普通受击动画并继续校准
```

## 模拟器中的缺口

原 `vpad.cpp` 没有实现或注册 `VPADSetGyroAngle`。运动后端原有角度来自 `MotionHandler.h` 的 IMU 欧拉角，其中 Y 值包含固定的 `-0.5f` 偏置。游戏每次要求清零却继续读到绝对角度，因而可能反复累加偏置。例如静止输入 `-0.5` 累加成 `-0.5/-1.0/-1.5`，任意两次的差都不满足 `0.05` 条件。这给出了箭已命中但靶子不破的一条明确代码原因。

原 `VPADSetGyroDirection` 只写入 `g_vpadGyroDirOverwrite`；该变量没有参与 `VPADRead` 的方向输出。因此游戏请求将当前持握姿态设为单位方向时没有生效，可保留用户观察到的约 90° 初始偏移。固定补偿某一个方向无法正确处理不同持握姿态。

公开接口定义参见 [devkitPro/wut 的 VPAD 头文件](https://github.com/devkitPro/wut/blob/master/include/vpad/input.h)：角速度字段位于 `0x38`，角度字段位于 `0x44`，方向矩阵位于 `0x6c`。

## 修复范围

- 实现并注册 `VPADSetGyroAngle`，使 `VPADRead` 以游戏指定的角度重新建立参考点，之后保留连续累计角度，包括超过一整圈的转动。
- 实际应用 `VPADSetGyroDirection`。VPAD 的方向基向量按行保存：设校准时原始矩阵为 `R0`、游戏请求矩阵为 `D`，修正矩阵为 `transpose(R0) * D`，之后输出 `R * correction`。由四元数生成的宿主方向基为正交基，转置即其逆。
- 两个通道分别保存参考状态；读取和重置共用锁；重新映射 VPAD 模块时清除状态。
- 后续格挡问题排查补充修正了运动后端的累计角度：现在逐轴积分去偏后的角速度；四元数姿态融合仍负责方向矩阵。未完整实现全部 VPAD 运动接口。
- 游戏资源和破碎条件保持原有逻辑。原始 ROM 未修改。

## 后续反馈：举起格挡后再次错位

用户反馈初始校准可用，但举起格挡后再次错位。进一步反汇编确认 `0x022644d0` 的加速度检查路径会在 `0x022646c8` 再次调用同一套角度、方向重置；这条路径与 `0x02263874` 的射击校准路径不同。单纯验证第一次归零不能覆盖这个过程。

通过真实 `WiiUMotionHandler` 加 `GyroAngleReference` 的独立运动回放，确认原累计角度还有独立的轴向错误：以每秒 100°、持续 1 秒绕传感器 Y 轴转动，原程序给出相对角度 `(0, 0, -0.277771)`，但对应 VPAD 角速度的正确积分应是 `(0, -0.277778, 0)`。前者把 Y 轴转动错误地报告在 Z 轴。原实现从四元数中抽取欧拉角，不能代替按传感器机体轴积分得到的累计角度；大倾斜时还涉及欧拉角分支变化。

已将 `MotionHandler.h` 的角度输出改为分别积分去偏后的 X/Y/Z 角速度，采用与 `getVPADGyroChange` 相同的符号和单位。方向矩阵继续来自原有四元数融合。相应取消 `GyroAngleReference` 对角度差取余；累计角度可以跨越多个整圈，不能当成周期欧拉角折返。

修改后同一 Y 轴回放输出为 `(0, -0.277778, 0)`，放回后的残差约 `1.49e-8` 圈。扩展检查覆盖三轴各转过 120°再返回、陀螺仪独立输入、带重力加速度反馈、举起时清零、同时多轴转动以及四元数方向回位，均通过。原有有限采样率的重力融合在急转回位时约有 0.21°残差，方向检查上限明确设为约 0.3°；没有把理想数值检查宣称为手机实测。

本轮完整 Release 编译和链接已通过，运行包中的 Cemu.exe 已更新，前一轮版本备份为 `out/diagnostics/game-wario-gyro/Cemu.before-motion-integration.exe`。实际游戏的格挡后瞄准仍待用户复测；目前确认修复的是在回放中复现的累计角度轴向错误。

- 初始校准、`0x02263874` 的射击校准和游戏其他格挡逻辑保持原调用路径。

## 第四轮反馈：炮弹成功格挡后仍累积小偏移

用户先报告大幅错位改善，随后确认每次格挡后仍增加少量偏移并保持，进一步限定为“格挡大炮发射的炮弹之后”。前一轮兼容处理不能记为完整修复。

继续检查本地 ROM：`0x02266428` 是炮弹接近玩家后的状态处理；成功防御分支检查 Arrow 场景 `+0x1e3a`，执行音效调用、`0x022664b8 -> 0x027727d4` 的 `SignUpDRC` 震动请求，然后改变炮弹状态。这个分支没有直接调用方向或角度重置。当前 Moonlight 会话能力报告 `rumble=0`，所以不能据此认定手机物理震动引起了偏移。

为区分成功命中、举盾重置和运动融合变化，新增精确诊断入口：成功格挡处记录 `Cannonball blocked`，Arrow 每 6 帧记录游戏实际保存的角度、方向、校准累计值、射击向量和弓模型矩阵。所有入口由标题、RPX hash 和原始指令签名限定，保持客体寄存器并跳入原始函数，未改写命中结果或偏移数值。诊断输出受 Input API 日志开关控制。

新增观测尚需实际复现；目前不能判断剩余偏移来自游戏流程、运动采样还是姿态融合。
## 第五轮：与格挡无关的转动回位累计误差

用户修正现象：手机转动后回到原姿势，瞄准每次增加少量偏移；不能继续将炮弹成功格挡认定为必要触发条件。第四轮确实抓到两次炮弹成功格挡，但当时没有独立物理姿态基准，不能据此建立因果关系。

已确认远程输入路径会丢失收到的中间体感数据：主机请求陀螺仪和加速度计各 100 Hz；原 Runtime 只有最新 CgpInput 快照，边沿队列仅保存按钮和触摸；RemoteController 在客体 VPADRead 更新状态时，对当前快照做一次积分。一次读取间隔中收到多份角速度时，中间值被覆盖，转向和回程可以留下不对称的积分误差。

修复实际主机到适配器路径：

- 主机为每次陀螺仪或加速度计更新保留一份有序快照，与按钮/触摸边沿独立；队列有 512 份上限，超限明确记录并停止会话，不静默覆盖。
- C ABI 结构和函数表布局不变，minor 升为 1：read_input consumer 3 消费体感，空队列返回 CGP_IDLE。适配器明确要求 1.1，避免旧 DLL 被误当成支持完整采样。
- RemoteController 在已有独立输入线程中持续排空体感队列，即使游戏暂停也继续计算；按每份传感器时间戳更新真实 WiiUMotionHandler。读取队列时以传感器事件时间判断分量新鲜度，不以延迟到达消费端的墙钟丢弃历史。
- 解绑、断开、超时和新会话清除待消费数据；新代际重新初始化运动状态。
- 本轮移除仅用于第四轮调查的炮弹/逐帧客体诊断钩子。先前有实际大角度错位记录支持的日版举盾方向兼容处理暂时保留。

独立回放使用实际 MotionInputQueue、RemoteMotion 和 WiiUMotionHandler，三轴分别做 10 次转出/返回，100 Hz 传感器、60 Hz 消费，并包含一次 250 ms 消费停顿。每轴收到/消费 1001 份；旧快照路径留下约 1.79979° 累计角度误差，新队列与完整采样参考的差为 0，回位角度误差为 0。队列清空、代际中性返回和明确溢出检查通过。该结果只证明收到的转动数据不再因帧间覆盖丢失，不等于手机真实姿态零漂已经全部消除。

回放代码和输出位于 out/diagnostics/game-wario-gyro/remote-motion-queue-test.cpp/.exe。完整构建及手机复测状态见交付元数据；实际“来回转动后瞄准是否仍逐次偏离”仍待本轮用户确认。
### 补充：方向矩阵的数值积分误差

进一步直接检查瞄准使用的方向矩阵，而非仅检查累计角度。100 Hz 输入、60 Hz 消费，重复 10 次同轴 90°转出/返回，转出用 47 份、返回用 33 份采样：旧快照路径累计角度误差约 44.5069°。完整队列保留所有数据后，累计角度仅有约 0.000330247°浮点残差，但原姿态更新仍留下约 0.08614–0.08625°的方向残差。

原因：MahonySensorFusion 使用 q += q*(0,gyro*dt/2) 再归一化，实际转过的角度为 2*atan(|gyro|*dt/2)，快转比慢转少转得更多；转出和返回速度不同时，这个误差不会抵消。现改为对修正后的角速度计算有限旋转四元数并与当前姿态相乘，保留原有去偏、死区、重力反馈、时间上限及归一化。

相同实际类回放修改后，三轴方向回位残差分别为 0°、约 0.00000170755°、约 0.00000170755°；累计角度与完整采样参考一致。此前 120°举起放下、重力反馈、举起清零和同时多轴运动回归也通过。该数值更新位于共享 MahonySensorFusion，因此也被使用该类的其他体感后端采用；不是仅对游戏画面添加反向偏移。

补充回放代码：out/diagnostics/game-wario-gyro/remote-motion-direction-test.cpp；原数值更新备份：同目录 Mahony.before-exact-rotation.h。真实手机的传感器偏置、传输时序和持握回位误差不由这些理想输入检查排除，不能据此宣称手机实测已通过。
## 第六轮：用户明确是“射完再取下一箭”时换方向

本轮用户明确纠正：持续瞄准时没有偏移，偏移出现在射完一箭、准备下一箭时；此前“来回转动累计误差”的归因不适用于这个实际触发条件。第五轮构建用户实测仍有问题，不能记为已解决。

重新沿本地 ROM 追踪，已把触发时机从“射击校准”具体定位为“开始按住弓、取下一箭”：

- `0x02262f78–0x02262f9c` 根据当前触摸和前次触摸状态生成新按下标记，存到弓状态 `+0x1e29`。
- `0x022637fc` 检查此标记，`0x02263814` 检查触摸 X 坐标至少为 420；随后通过 `0x02263284` 检查场景模式为 1 且脚本校准标志 `+0x2253` 开启。
- 满足这些条件时，保存当前三轴角度后，`0x02263874` 调用 `0x020299b0`，要求角度清零、方向设为单位矩阵、方向修正基准设为单位矩阵。这条路径将开始取箭时的朝向当作新的正前方参考，没有检测电视实际位置的步骤。
- 因而先前仅保留格挡方向基准，并不能阻止下一次取箭时再覆盖方向。用户最新触发条件与此路径及已记录 SetDirection 的 guest SP `0x0e201030` 相符。
- 15:25:12.266 的起弓重置后，两个相邻观测样本中原始方向只变化约 2.46°，游戏输出方向却变化约 15.23°；这与参考方向被改写一致，不能称为这 0.1 秒内的积分累计误差。

| 当前完整算法 | +23.1919° |

新生产路径逐份匹配无加速度姿态反馈的隔离算法（45,213 份矩阵最大差 0）；另逐份比较游戏原始加速度，确认与原路径一致。程序及结果见同目录 `gravity-isolation-replay.cpp/.exe`、`gravity-isolation-replay-results.csv`；上一轮对照结果为 `no-bias-replay-results.csv`。
